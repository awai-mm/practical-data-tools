# 第6章 現場で実際に起きたトラブル事例と完全復旧ケーススタディ

公開前の検品で難しいのは、問題を見つけることだけではない。指摘を修正担当者に伝え、修正版を取り違えずに確認し、公開済みのページまで復旧したと証明する必要がある。本章では、実務で起こりやすい事故を、検証用の数値を用いた三つの再構成事例として扱う。特定企業の実績を示すものではない。

各事例で共通する原則は、検出件数と影響範囲を分けて記録することだ。`missing_alt_count=3`は属性がない画像要素が三つあることを意味し、三ページに問題があるという意味ではない。また、検査が途中で失敗したページをゼロ件として扱ってはならない。「問題なし」と「確認できなかった」は、運用上まったく異なる状態である。

## 6.1 監査結果の読み方を先に固定する

必須カラムは次の八つとする。文字数はHTMLの文字参照を復元し、前後の空白を除いた文字列をPythonの`len()`で数える。表示幅や検索結果での表示文字数を保証する値ではない。

| カラム | 定義 | 判定上の注意 |
|---|---|---|
| page_id | ページを追跡する固定識別子 | URL変更後も原則維持する |
| url_path | 検査対象の公開パス | クエリ付きページの扱いを別途決める |
| title_length | title本文の文字数 | 未設定と空文字はともに0になる |
| meta_desc_length | descriptionの文字数 | 重複指定は別の指摘で残す |
| h1_count | h1要素数 | 件数だけで構造の適否は断定しない |
| missing_alt_count | alt属性がないimg要素数 | `alt=""`とは区別する |
| dummy_link_count | 仮リンク規則に一致するa要素数 | 同一URLも出現ごとに数える |
| ogp_complete | 必須OGP四項目が非空か | 到達性や画像の妥当性は別途確認する |

本書の運用例では、titleは1〜35文字、descriptionは1〜120文字、h1は一つを公開前の社内基準とする。これは検索サービスやHTMLの普遍的な制限ではない。見出し階層の飛びも、ただちに仕様違反と断定せず、文書の構造を確認するための指摘として扱う。

OGPの必須項目は`og:title`、`og:type`、`og:url`、`og:image`とする。四つが存在していても、古い画像や検証環境のURLを指している可能性がある。八カラムは監査の入口であり、完全な品質保証ではない。

## 6.2 ケース1：共通テンプレートの差し替えでメタ情報が逆戻りした

### 失敗シナリオと発見

外注先から納品された24ページのLP群で、初回検品時には各ページ固有のtitleとdescriptionが設定されていた。その後、公開直前に共通ヘッダーの表示崩れが見つかり、制作担当者が古いテンプレートを使って再出力した。

目視確認は修正対象のヘッダー周辺だけに集中した。結果として、18ページのtitleが長い共通文言へ戻り、6ページのdescriptionが消え、12ページからOGP設定が抜けた。各件数には重複があるため、合計36ページの不具合と数えてはいけない。

| page_id | url_path | title_length | meta_desc_length | h1_count | missing_alt_count | dummy_link_count | ogp_complete |
|---|---|---:|---:|---:|---:|---:|---|
| lp-001 | /service/a/ | 62 | 0 | 1 | 0 | 0 | false |
| lp-002 | /service/b/ | 59 | 142 | 1 | 0 | 0 | false |
| lp-003 | /service/c/ | 31 | 96 | 1 | 0 | 0 | true |

公開後、担当者が共有プレビューを確認して初めて異常に気づいた。ページ本文は正しく表示されていたため、通常の画面確認では発見できなかった。

### 原因分析

直接の原因は古いテンプレートへの差し戻しだったが、管理上の問題は三つあった。第一に、検品済みファイルと公開ファイルの対応が記録されていなかった。第二に、共通部分の修正を局所的な変更と見なし、全ページの再検査を省略した。第三に、OGPの有無だけを確認し、公開URLと画像の組み合わせを確認していなかった。

「初回納品は合格だった」という事実は、後続の成果物を保証しない。検査結果はページの名前ではなく、その時点の成果物に結び付ける必要がある。

### 完全復旧までの手順

1. 公開中の24ページと直前の納品物を保存し、影響範囲を確定する。
2. 検品済みのメタ情報を基準に、最新版テンプレートへ修正を適用する。
3. 全24ページを再検査し、共通修正による別の欠落がないか確認する。
4. 修正版を配置し、公開URLから取得したHTMLを再検査する。
5. OGP画像の応答、画像内容、共有先のプレビューを確認する。
6. 成果物の識別情報、検査日時、承認者を復旧記録に残す。

修正後は、titleが24〜34文字、descriptionが72〜112文字に収まり、24ページすべてで必須OGPがそろった。ただし、共有先に古い情報が残る場合は、HTML修正の完了とプレビュー更新の確認を別の状態として管理する。外部キャッシュの反映を待っている間に、復旧全体を完了扱いにしない。

再発防止策として、共通テンプレートを変更した場合は対象全ページを再検査する規則を追加した。合格報告には成果物のハッシュ値を付け、公開担当者が別のファイルを選んだ時点で、検査済みという扱いを引き継げないようにした。

## 6.3 ケース2：部品の組み合わせで見出しと画像説明が崩れた

### 失敗シナリオと発見

商品紹介ページを12ページ制作する案件で、メインビジュアルと導入事例の部品が別々に作られた。各部品は単体では自然に見えたが、それぞれにh1が含まれていた。さらに、説明欄の見出しは文字サイズを合わせる目的でh2からh4へ変更されていた。

画像については、装飾画像に`alt=""`が付いている一方、商品写真と図解の一部にはalt属性そのものがなかった。画面上の見た目が同じであるため、レビューでは区別されなかった。

| 検査項目 | 修正前 | 修正後 | 確認方法 |
|---|---:|---:|---|
| h1が二つあるページ | 8 | 0 | 文書全体の要素数 |
| 見出し階層が飛ぶページ | 5 | 0 | 見出しの出現順 |
| alt属性がない画像要素 | 27 | 0 | img属性の有無 |
| 空のaltを持つ画像要素 | 19 | 23 | 用途を見て個別判断 |

修正後に空のaltが増えているのは、四つの装飾画像に明示的な空文字を設定したためである。すべての画像に説明文を入れることが改善とは限らない。

### 原因分析

部品の設計書に、ページ全体での役割が定義されていなかった。見出しレベルが文字の大きさとして扱われ、文書構造と見た目が混同されていた。また、検品表には「画像説明を確認」としか書かれておらず、属性欠落、空文字、不適切な説明文が一つの項目にまとめられていた。

h1が複数あることだけで、すべてのページを不適切と断定することも避けるべきだ。この案件では「ページの主題を示すh1は一つ」という設計方針があったため、その方針との不一致として修正対象にした。

### 完全復旧までの手順

最初に、ページごとの主題と節の構成を文章で書き出した。次に、メインの題名をh1、主要な節をh2、節内の小見出しをh3へ整理した。文字サイズはCSSで維持し、構造変更が見た目の退行を引き起こさないようにした。

画像は、商品を説明する画像、本文と同じ情報を繰り返す画像、装飾画像、リンクとして機能する画像に分けた。商品写真には必要な特徴を簡潔に記述し、装飾画像には空のaltを設定した。リンク画像では、画像の外観より移動先や操作目的が伝わる表現を優先した。

再検査では、12ページすべての構造検査に加え、代表ページで見出し一覧と読み上げ順を確認した。`missing_alt_count=0`だけを合格理由にせず、「画像」「写真」といった役に立たない説明が残っていないかも確認した。

再発防止として、部品の仕様に使用可能な見出しレベルと画像の役割を追記した。部品単体の検査に加えて、実際に組み合わせた完成ページを必ず検査する工程を設けた。

## 6.4 ケース3：仮リンクの除去が本物の導線まで壊した

### 失敗シナリオと発見

キャンペーンサイト40ページで、公開前のリンク検査から63件の仮リンク候補が見つかった。担当者は文字列の一括置換で対応しようとしたが、ページ内リンクまで削除対象に含めてしまった。

| 候補の種類 | 件数 | 正しい対応 |
|---|---:|---|
| `href="#"` | 21 | 実URLへの置換、または操作部品へ変更 |
| `https://example.com/...` | 16 | 確定した公開先へ置換 |
| 有効な`#section` | 18 | 対象IDを確認して維持 |
| 存在しないIDへの参照 | 8 | 参照先またはIDを修正 |

単に`#`を含むかどうかで判定すると、有効なページ内リンク18件まで仮リンクと誤認する。一方、`dummy_link_count`を`#`と例示ドメインだけの検出に限定する場合、存在しないIDへの参照8件は別の検査で拾う必要がある。

### 原因分析と復旧

問題の根本は、「リンクの種類」と「リンクが正しく機能するか」を同じ検査に押し込めたことだった。仮URLの検出、ページ内参照の整合性、外部URLの応答確認は、異なる判定である。

復旧ではまず、一括置換前の版と比較して18件の正常な導線を戻した。続いて37件の仮リンクを確定URLまたは適切な操作要素へ変更し、8件の参照先不一致を修正した。最後に、申込、資料請求、戻る導線を実際に操作した。

公開先での確認では、リンク先が応答していても、別商品の申込画面へ移動していないかを調べた。応答コードが正常であることと、業務上正しい到達先であることは別の条件だからだ。

再発防止策は、仮リンクを残す場合に管理票へ担当者と確定期限を登録すること、ページ内リンクを専用の検査へ分離すること、一括置換後には差分と主要導線を確認することである。

## 6.5 復旧完了を判断する共通条件

三つの事例はいずれも、数値をゼロにするだけでは復旧しない。対象ページがすべて検査され、公開された成果物と検査対象が一致し、主要な操作と情報表示が確認できて初めて完了とする。

表記揺れも同様だ。「お問い合わせ」と「お問合せ」の混在を統一しても、引用文や固有名詞まで書き換えてはならない。承認された表記辞書と例外を用意し、機械的な候補抽出の後に文脈を確認する。

復旧記録には、発見時刻、対象範囲、原因、修正内容、再検査結果、残課題を残す。例外を認める場合は、対象ページ、理由、責任者、期限を明記する。この記録があれば、次の担当者は同じ問題を最初から調査せずに済む。
