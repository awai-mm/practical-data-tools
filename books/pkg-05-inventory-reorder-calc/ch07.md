# 第6章 現場で実際に起きたトラブル事例と完全復旧ケーススタディ

欠品と過剰在庫は、計算式を修正するだけでは解消しない。出庫実績の意味、在庫の計上時点、発注残の扱い、入荷までの日数がそろって初めて、安全在庫と発注点が機能する。本章の3件は、現場で生じる典型的な失敗を、検証できる数値に置き換えた教材用の再構成事例である。特定企業の実録ではない。

## 6.1 ケーススタディで共通して使う計算条件

日次需要が独立で、需要分布と調達条件が大きく変化しない場合、固定リードタイムの安全在庫は次式で近似する。

- 安全在庫：`z × demand_stddev × √lead_time_days`
- 発注点：`avg_daily_demand × lead_time_days ＋ 安全在庫`
- 在庫ポジション：`current_stock ＋ 有効発注残 − 未出庫引当`
- 目標在庫：`avg_daily_demand × (lead_time_days ＋ R) ＋ z × demand_stddev × √(lead_time_days ＋ R)`

`R`は次回見直しまでの日数である。本章では整数個を扱い、安全在庫・発注点・目標在庫をそれぞれ切り上げる。推奨発注数は、在庫ポジションが発注点以下の場合に、目標在庫との差を発注単位へ切り上げる。日次判定でも判定間隔中の需要は発生するため、欠品の影響が大きい商品では、その間隔を含む設計を別途検証する。

ここで使う`z = 1.65`は、正規近似における片側約95％の水準である。これは補充サイクル中に欠品しない確率の目安であり、注文数量の95％を必ず出荷できるという意味ではない。

必須8カラムだけでは、発注残、引当、欠品期間、売上金額を把握できない。これらは別の明細から補完する。また、`moq`は本来「最低発注数量」であり、発注倍数と同義ではない。以下では仕入条件を確認し、「最低数量と発注倍数がともに同じ値」の商品に限定する。

## 6.2 事例1：欠品日の出庫ゼロを、需要ゼロとして学習した

### 発生した症状と数値

交換用フィルターの出庫実績30日分から日次需要を集計したところ、平均は8個だった。しかし、10日間は欠品しており、販売できなかっただけである。欠品日はゼロとして平均に含まれ、再入荷後も発注点が低い状態が続いた。

| 項目 | 復旧前 | 復旧後 |
|---|---:|---:|
| sku_code | FLT-101 | FLT-101 |
| item_name | 交換用フィルター | 交換用フィルター |
| current_stock | 70個 | 70個 |
| avg_daily_demand | 8個／日 | 12個／日 |
| demand_stddev | 6個／日 | 4個／日 |
| lead_time_days | 7日 | 7日 |
| unit_cost | 500円／個 | 500円／個 |
| moq | 20個 | 20個 |

復旧前の安全在庫は`1.65 × 6 × √7`を切り上げて27個、発注点は83個となる。復旧後は安全在庫18個、発注点102個である。標準偏差が小さくなっても、平均需要を正しく戻すと発注点は上がる。

見直し間隔を7日とすると、復旧前の目標在庫は150個、復旧後は193個となる。発注残と引当がない場合、推奨発注数は80個から140個へ増える。低い平均値のままでは、毎回補充しているのに欠品を繰り返す。

### 原因分析

問題は計算式ではなく、需要の観測方法にあった。出庫実績は「出荷できた数量」であり、「顧客が必要とした数量」とは限らない。欠品によって観測が打ち切られた日のゼロを、通常の需要として扱っていた。

ただし、欠品日を除外して平均を計算するだけでも十分ではない。需要が多い日ほど欠品しやすく、残った日の平均にも偏りが生じる。この事例では、受注日時と希望数量を復元し、重複注文やキャンセルを整理して需要系列を作り直した。その結果が平均12個、標準偏差4個である。

### 完全復旧までの手順

1. 対象商品の発注確定を一時保留し、手持在庫と未処理受注を照合する。
2. 欠品開始・解消時刻を特定し、30日間の受注と出庫を日別に突合する。
3. 希望納期基準の需要系列を作り、翌日への繰越注文を二重計上しない。
4. 修正後の発注点で不足を判定し、通常便と緊急便を分けて手配する。
5. 修正前後の値、使用した明細、承認者、適用日を履歴に残す。

現在庫70個は平均需要の約5.8日分しかなく、通常の調達には7日かかる。140個を通常発注するだけでは、到着までの欠品を解消できない。入荷日までの日別残高を作り、必要な緊急移送や納期調整も実施して復旧を完了する。

### 再発防止

日次集計には欠品フラグと受注残を付ける。欠品期間を含む商品は通常の出庫平均をそのまま採用せず、受注データの品質を確認する。失注を記録できない場合は、推定値であることと不確実性を明示し、担当者の確認対象にする。復旧判定は、在庫が一度増えた時点ではなく、複数の補充サイクルで欠品と在庫推移が安定した時点で行う。

## 6.3 事例2：平均リードタイムだけを使い、納期遅延を吸収できなかった

### 発生した症状と数値

包装資材では日次需要が安定していた一方、仕入先の出荷集約によって納期がばらついていた。マスターには平均5日だけを登録し、需要変動に対する安全在庫しか持っていなかった。

| 指標 | 設定・実績 |
|---|---:|
| 平均日次需要 | 20個 |
| 日次需要の標準偏差 | 3個 |
| リードタイムの平均 | 5日 |
| リードタイムの標準偏差 | 2日 |
| 現在庫 | 130個 |
| 発注残／未出庫引当 | 0個／0個 |
| 仕入単価／moq | 200円／50個 |

固定5日とした安全在庫は12個、発注点は112個である。現在庫130個では発注対象にならない。しかし、今回の入荷所要日数が9日なら、平均需要だけでも180個必要になる。

需要とリードタイムが独立しているという前提では、リードタイム中の需要分散を次式で近似できる。

`平均リードタイム × 日次需要分散 ＋ 平均日次需要² × リードタイム分散`

数値を入れると`5 × 3² ＋ 20² × 2² = 1,645`となる。安全在庫は`1.65 × √1,645`を切り上げて67個、発注点は167個となり、130個は発注対象に変わる。

### 原因分析

発注担当者は「需要が安定している商品だから安全在庫は少なくてよい」と考えていた。しかし、不確実性は需要側だけにあるわけではない。工場の出荷待ち、輸送、検収待ちも、在庫を消費し続ける期間を延ばす。

さらに、仕入先の出荷日を入荷日として集計していた。実際に使えるのは検収が終わった後であり、帳票上の納期と利用可能になるまでの日数が一致していなかった。

### 完全復旧までの手順

まず、発注確定から利用可能までの時間を、暦日で再集計する。分納については、初回入荷で全量がそろったものとして扱わず、数量ごとの利用可能日を記録する。未入荷の遅延案件を集計対象から落とすと短い納期だけが残るため、未完了案件も別表で監視する。

次に、需要と納期の独立性を確認する。繁忙期に注文量が増え、同時に納期も延びる商品では、上記の近似だけでは不足し得る。その場合は過去の補充期間ごとの需要量を直接検証し、季節別の設定を検討する。

見直し間隔7日の場合、納期変動を含む目標在庫は309個となる。現在庫130個との差179個を50個単位へ切り上げると、推奨発注数は200個である。ただし、これも到着前の不足を解決する数量ではない。既存受注への対応と将来の補充を分けて管理する。

### 再発防止

必須カラムの`lead_time_days`には平均日数を保持し、標準偏差、観測件数、対象期間は仕入先別の補助表で管理する。月次で平均とばらつきを更新し、遅延件数が急増した場合は臨時見直しを行う。復旧後は安全在庫の増加額も確認し、納期短縮交渉と在庫積み増しの費用を比較する。

## 6.4 事例3：発注残の欠落とABC集計の誤りで、在庫が積み上がった

### 発生した症状と数値

高単価の交換部品で、夜間バッチが毎日同じ不足を検知し、重複発注が起きた。加えて、売上貢献度によるABC分類のはずが、在庫数量と仕入単価の積で分類されていた。

| 項目 | 数値 |
|---|---:|
| 平均日次需要／標準偏差 | 2個／1個 |
| リードタイム／見直し間隔 | 10日／7日 |
| 現在庫 | 18個 |
| 有効発注残 | 100個 |
| 未出庫引当 | 4個 |
| 仕入単価／moq | 10,000円／50個 |

安全在庫は6個、発注点は26個、目標在庫は41個となる。在庫ポジションを現在庫18個だけで判定すると、不足23個を50個へ切り上げて発注する。しかし、正しい在庫ポジションは`18 ＋ 100 − 4 = 114個`であり、追加発注は不要だった。

### 原因分析

在庫データの更新は毎晩だったが、発注残は週次でしか取り込んでいなかった。発注が受理された事実を翌日の計算が認識できず、入荷まで同じ不足を再検知していた。

ABC分類にも別の誤りがあった。売上貢献度を求めるには、対象期間の売上金額が必要である。`current_stock × unit_cost`は在庫評価額であり、売上ではない。大量に抱えた商品ほど上位に分類され、過剰在庫が重点補充の根拠になってしまった。

### 完全復旧までの手順

発注受付番号をキーに仕入先の受注残と照合し、重複分を特定する。取消可能な数量、取消費用、返品条件を確認してから変更する。全件を一括で取り消すと、本来必要だった最初の注文まで失うおそれがある。

ABC分類は返品や値引きを反映した期間売上で再計算する。例えば累積売上構成比80％までをA、95％までをB、それ以降をCとする場合、境界をまたぐ商品の所属と同額商品の並び順も規定する。売上データがない商品は未判定とし、仕入金額で代用しない。

在庫114個相当は平均需要の57日分である。ただし、発注残を含む114個と手持18個では、滞留の意味が異なる。保管中の滞留判定には最終出庫日、入荷日、ロット別残数を使い、将来の過剰見込みとは別に表示する。

### 再発防止と復旧完了条件

再発防止には、発注残の毎日更新に加え、同じ処理識別子から発注を二重登録しない仕組みが必要である。入荷時は発注残を減らし、在庫を増やす処理の時点をそろえる。

復旧完了は、重複注文の処置、在庫・発注残・引当の一致、ABC分類の再計算、再実行時の重複防止を確認して判定する。「計算結果が正常になった」だけでなく、外部に残った注文と帳簿まで整合させることが完全復旧である。
